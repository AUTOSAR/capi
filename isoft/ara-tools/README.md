## Overview

`configMachine` is a machine configuration tool in the AUTOSAR Adaptive Platform (AP) toolchain. For a specified machine, it reads ARXML model files and invokes the generator (`aragen`) to produce the related manifest files, searches for the required executables, and copies the manifests and executables to the `ara-sysroot` directory as the runtime of the target Machine, including:
- executables
- various manifests, such as executable manifests, service instance manifests and machine manifest etc.
- boot configuration (`ara_ver1.json`)

The tool organizes all runtime-required files following the software cluster structure, enabling the target machine to boot and run directly.

## Features

- **Automatic SWCL Integration** — Parses software cluster information from ARXML models and automatically integrates framework, core, and application-level software clusters
- **Framework Sharing** — The `--withSDK` option enables multiple machines to share the same framework software cluster
- **Boot Configuration Generation** — Automatically generates versioned boot configuration files (`ara_ver1.json`) and checksum files
- **QoS Support** — `--qos-path` passes a QoS file to the underlying `aragen` generator
- **Flexible Logging** — Supports `--log`, `--quiet`, and `--debug` for detailed or suppressed logging control

## Prerequisites

Before using `configMachine`, ensure the following are prepared:

| Requirement              | Description                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| **ARXML Model Files**    | Directory containing AUTOSAR ARXML files with machine, software cluster, process, and executable definitions                     |
| **Compiled Executables** | Build output directories containing executables for each software cluster                                                        |


## Command-Line Arguments

### Required Arguments

| Argument                        | Shorthand | Description                                                                                                                                     |
| ------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `--ara_sysroot <path>`          | `-r`      | AP system root directory path                                                                                                                   |
| `--machine <fqn>`               | `-m`      | Fully Qualified Name (FQN) of the target machine, e.g. `/ISOFT/Development/Machine1`                                                            |
| `--workdir <path>`              | `-w`      | Working directory for intermediate artifacts and temporary files                                                                                |
| `--executable-build-dirs <dirs>`| `-e`      | Source directories for executables, multiple directories separated by commas. The tool searches for executables by FQN within these directories |
| `<files>`                       | —         | A list of input files or directories containing ARXML model files (positional argument, multiple allowed)                                       |


### Optional Arguments

| Argument                  | Shorthand | Description                                                                                                                     |
| ------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `--withSDK <path>`        | —         | Specifies the directory of the existed SDK. When set, the framework software cluster under the specified path is used directly. |
| `--canUseExistingExe`     | —         | Allows using pre-existing executables. By default, directories specified in `--executable-build-dirs` must contain all executables; when this option is enabled, if an executable cannot be found in the build directories, the existing executable in the software cluster directory is preserved.  |
| `--keep-ara-gen-output`   | —         | Retains the intermediate configuration information generated by `aragen`, skipping cleanup of `workdir`                         |
| `--qos-path <path>`       | —         | The QoS file path that will be passed to `aragen`                                                                               |
| `--verbose` / `-v`        | `-v`      | Increases logging verbosity. Can be repeated (e.g. `-v -v`) for more detailed output                                            |
| `--log <file>`            | `-l`      | Write all log data to the specified file                                                                                        |
| `--quiet`                 | `-q`      | Suppress all logging output to console (overrides `--verbose`)                                                                  |
| `--debug`                 | `-d`      | Specify detailed logging configuration                                                                                          |
| `--help`                  | `-h`      | Show help message and exit                                                                                                      |

## Output Artifacts

After configuration completes, the following content is generated under `ara-sysroot/ara/`:

```
ara-sysroot/
└── ara/
    ├── ara_ver1.json                   # Boot configuration file (JSON format)
    ├── ara_ver1.md5                    # Boot configuration checksum file
    ├── framework/                      # Framework software cluster, present when --withSDK is not specified
    │   ├── ara_loader                  # Ara loader 
    │   ├── VERSION                     # Version marker
    │   ├── swcl_status.json            # Framework SWCL status
    │   └── <version>/                  # e.g. 1.0.0
    │       ├── swcl_manifest.json      # Software cluster descriptor
    │       ├── bin/                    # Executables
    │       ├── etc/                    # empty
    │       ├── include/                # Header files
    │       ├── lib/                    # Libraries
    │       ├── sbin/                   # System executables
    │       └── share/                  # Shared data (e.g. ARXML models)
    ├── core/                           # Core software cluster
    │   ├── swcl_status.json            # Core SWCL status
    │   └── <version>/                  # e.g. 1.0.0
    │       ├── swcl_manifest.json
    │       ├── bin/
    │       └── etc/
    │           ├── run_time_framework_core_list.json      # Framework/Core SWCL list
    │           ├── run_time_application_swcl_list.json    # The link to the application SWCL list under swcls/
    │           ├── run_time_application_swcl_list.md5     # Application SWCL list checksum file
    │           ├── function_groups.json                   # Function group definitions
    │           ├── machine_manifest.json                  # Machine manifest
    │           ├── *.json                                 # Other manifests
    └── swcls/                          # Application-level software clusters
        ├── run_time_application_swcl_list_ver1.json       # Application SWCL list
        └── <swcl_name>/                # e.g. os, diag, app1
            ├── swcl_status.json        # Per-SWCL status
            └── <version>/              # e.g. 20.4.2
                ├── swcl_manifest.json
                ├── bin/
                └── etc/
                    └── <process_name>/   # Manifest files for each process
```


## Configuration Files

### `ara_ver1.json`

Machine boot configuration file, recording the paths and version information of framework&core software cluster.

### `swcl_manifest.json`

Software cluster descriptor, containing the cluster's metadata, dependency relationships, and lists of contained executables and processes.

### `swcl_status.json`

Per-software-cluster status file, located at the software cluster root directory (e.g. `framework/swcl_status.json`, `core/swcl_status.json`, `swcls/os/swcl_status.json`). It records the currently active version and integration state.

### `run_time_framework_core_list.json`

Framework and Core software cluster list. Generated under the core software cluster's `etc/` directory.

### `run_time_application_swcl_list_ver1.json`

Application-level software cluster list, recording all integrated application-level software clusters with a structure similar to the Framework and Core software cluster list. Located at `ara/swcls/run_time_application_swcl_list_ver1.json`.


## Examples

### Basic Usage

For users, in most cases, they develop business code based on the SDK. Therefore, during development, they often need to compile their own applications and update their configurations.
When the code is modified or the model changes, users need to copy the built application and configuration to the correct place.

Following command is used to generate the configuration files based on arxmls files, and copy the executables, configuration files to the right place after SDK is ready:

```bash
./isoft/ara-tools/configMachine \
  -r "${ARA_SYSROOT}" \
  -m /ISOFT/Development/Machine1 \
  -w "${CAPI_BUILD_DIR}/tmp/machine1" \
  -e "${HOME}/.isoft/tmp/ara_binout" \
  --withSDK "${SDK_INST_DIR}/ara-sysroot" \
  --canUseExistingExe \
  "${SDK_INST_DIR}/ara-sysroot/ara/framework/1.0.0/share/ara-arxmls" \
  -v -v
```

This command will:

1. Use `${ARA_SYSROOT}` as the AP system root directory
2. Generate configuration for machine `/ISOFT/Development/Machine1`
3. Output intermediate artifacts to `${CAPI_BUILD_DIR}/tmp/machine1`
4. Search executables in `${HOME}/.isoft/tmp/ara_binout`
5. Use the existed SDK in `${SDK_INST_DIR}/ara-sysroot`, and reuse the framework software cluster in it 
6. Read model definitions from the specified ARXML directory `${SDK_INST_DIR}/ara-sysroot/ara/framework/1.0.0/share/ara-arxmls`
7. Run in verbose logging mode (`-v -v`)

### SDK Generation via `ap-all` build

This command is used during SDK generation after all Adaptive Platform components have been compiled successfully. It is typically executed as the final step of the `ap-all` build to generate the configuration files from the ARXML input and assemble the required executables and configuration files into the SDK package.

```bash
./configMachine \
  -r "${ARA_SYSROOT}" \
  -m /ISOFT/Development/Machine1 \
  -w "${CAPI_BUILD_DIR}/tmp/machine1" \
  -e "${HOME}/.isoft/tmp/ara_binout" \
  "${SDK_INST_DIR}/ara-sysroot/ara/framework/1.0.0/share/ara-arxmls" \
  -v -v
```

## FAQ

### Q: Error "framework software cluster not found"

The ARXML model does not define a framework-category (`ISOFT_FRAMEWORK`) software cluster, or the cluster is not associated with the target machine. check whether a 'ISOFT_FRAMEWORK' category software cluster is defined in the ARXML model and correctly associated with the target machine.

### Q: Error "core software cluster not found"

Same as above — check whether a 'PLATFORM_CORE' category software cluster is defined in the ARXML model and correctly associated with the target machine.

### Q: Error "executable not available"

The executable corresponding to a process cannot be found in the directories specified by `--executable-build-dirs`. Please verify:

1. The build directory paths are correct
2. The executables have been compiled
3. The executable FQN paths match the definitions in the ARXML model

### Q: Error "circular dependency detected"

A circular reference exists in the `dependsOn` relationships of software clusters. Check the software cluster dependency definitions in the ARXML model and eliminate the cycle.

### Q: What is the difference between using `--withSDK` and not using it?

| Aspect                                  | Without `--withSDK`                          | With `--withSDK`                                         |
| --------------------------------------- | -------------------------------------------- | -------------------------------------------------------- |
| Framework integration                   | Integrates the framework software cluster    | Skips integration, uses the specified directory directly |
| Use case                                | The generation of the SDK                    | Configure a machine with an existing SDK |
| `platform_framework` in `ara_ver1.json` | empty                                        | Get the path from the `--withSDK` path  |

### Q: How are multi-version software clusters handled?

When the ARXML model defines multiple versions of the same software cluster, the tool automatically selects the highest version for integration. Lower versions are ignored. 


### Q: Why are `ara_loader` and `VERSION` preserved under `framework/`?

These are framework-level lorder/version markers. `configMachine` intentionally does not overwrite them; it only integrates the framework software cluster's runtime contents (executables, manifests, libraries, etc.) under `framework/<version>/`.
